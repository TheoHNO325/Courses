# 少数民族语言翻译课程项目大纲

## 0. 项目定位与最终边界

本项目以“藏文—中文翻译”为主线，以“东巴文图像—中文语义释读”为扩展，目标是形成一套能够在本地运行、可复现实验、适合本科课程大作业展示的系统，而不是追求大厂级别的通用翻译器。

建议把项目拆成三层：

1. **必须完成**：藏文语料整理、分词器/Tokenizer 对比、NLLB 微调和分领域评测。
2. **建议完成**：HY-MT2 推理对照、CS336 Transformer 小模型、藏文 OCR 后接翻译的串联系统。
3. **有余力再做**：DongbaMIE 图文模型微调、东巴文图像分类/检测、统一平台 Demo。

这里的“风格”首先指翻译输出对不同语域的适配：现代新闻/说明文、佛教及古典文献、仪轨/祈愿文本、文学或宣传文本。风格不能只靠 NLLB 的语言标签解决，因此必须通过数据分域、风格标签或分域报告来验证。

全程原则：模型在本地运行，不依赖在线大模型 API；数据集按各自许可证使用，不把受限数据或模型权重重新公开发布。

## 1. 总体技术路线

```text
藏文 Unicode 文本
        │
        ├─ 数据清洗、文档级切分、领域/风格标签
        │
        ├─ Tokenizer 实验
        │      ├─ NLLB SentencePiece/BPE
        │      ├─ HY-MT2 tokenizer
        │      └─ CS336 自训 BPE
        │
        ├─ 基线与微调
        │      ├─ NLLB-200 distilled 600M（主模型）
        │      ├─ HY-MT2-1.8B（参考/可选 LoRA）
        │      └─ CS336 小型 Transformer（教学型对照）
        │
        ├─ 藏文 OCR（后续）
        │      └─ OCR 文本 → 藏中翻译模型
        │
        └─ 东巴文扩展
               └─ 图像 + 指令 → 结构化中文语义 / 中文释读
```

现阶段 CPU 只做数据、Tokenizer、评测和少量推理冒烟测试；真正的翻译微调等有 GPU 后再开始。CPU 阶段的结果要能直接复用于 GPU 训练，不重复整理数据。

## 2. 藏文模块：数据、Tokenizer 与分词实验

### 2.1 数据集分工与规模

| 数据/子集 | 规模 | 用途 | 注意事项 |
|---|---:|---|---|
| MITRA v2 过滤训练集 | 427,916 条、638 个文档 | 主训练集；先取 10k/100k，再跑全量 | 自动挖掘对齐，结构可靠但没有逐句人工语义校验 |
| MITRA v2 内部验证集 | 23,219 条、38 个文档 | 调参、早停、误差分析 | 与训练集无文档重叠 |

| FLORES-200 `bod_Tibt-zho_Hans` | dev 997、devtest 1,012 | 通用领域固定测试 | 只评测，不训练；CC-BY-SA-4.0 |

| Shajiu PublicCorpus 样例 | 已下载；约 100 条 | 现代藏中格式与质量观察 | 自定义研究条款；仅样例，不进入正式训练 |
| CUTE 藏文子集 | 已下载 2 个文件、约 24.61 GB | 合成/机器翻译语料消融候选 | 当前没有下载中文侧，不能形成藏中句对，也不能作黄金评测 |

当前数据的主要缺口是“现代、广域、人工高质量藏中平行语料”不足。因此报告中不能把 MITRA 的分数直接称为“所有藏文风格的综合能力”，必须同时报告通用 FLORES、古典/宗教 MITRA 和现代 Lotsawa 等分域结果。

### 2.2 需要比较的 Tokenizer

#### A. NLLB Tokenizer（主基线）

模型使用 `facebook/nllb-200-distilled-600M`，语言代码为：

- 藏文输入：`bod_Tibt`
- 简体中文目标：`zho_Hans`
- 繁体中文目标：`zho_Hant`

NLLB 使用预训练 SentencePiece/BPE 体系。它不是“先做藏文词语切分再翻译”，而是直接把 Unicode 文本编码为子词 ID。训练时必须使用 `text_target=...` 对目标文本编码，并在生成时使用正确的目标语言起始 token。其预训练上下文通常按不超过 512 个 token 处理，因此需要在数据统计中检查长句截断。

#### B. HY-MT2 Tokenizer（第二基线）

使用 `tencent/Hy-MT2-1.8B` 做本地推理对照，必要时再做 LoRA。它是因果语言模型，不是 NLLB 式的 Encoder-Decoder；输入通常包含“把某语言翻译成某语言”的指令和源句，输出由生成过程产生。

分词比较时要分开记录两种数字：

1. **裸藏文长度**：只编码原始藏文，便于和 NLLB/CS336 比较。
2. **实际 prompt 长度**：包括任务指令、语言名和特殊 token，便于估算真实显存和上下文开销。

不能把 HY-MT2 的 prompt token 直接当成藏文分词效率，也不能把 HY-MT2 的 tokenizer 当作 NLLB 的可替换组件。HY-MT2 的优势是许可证（Apache-2.0）和统一指令式推理，代价是 1.8B 模型较重、实验开销更大。

#### C. CS336 自训 BPE（教学型对照）

沿用已有 assignment1 的 BPE 实现，至少做以下两种输入：

- **Raw Unicode BPE**：保留藏文 Unicode、tsheg、标点和组合字符的原始序列。
- **Syllable-aware BPE**：把 `་` 等可靠的音节边界作为显式分隔或特殊边界符，再训练 BPE。

建议初始词表做 4k、8k、16k、32k 四档；若 CPU 时间紧张，先做 8k/16k。CS336 模型的目的不是超过 NLLB，而是展示“语料、预分段和词表大小怎样影响低资源语言的编码与翻译”。

### 2.3 分词实验具体探索

#### 2.3.1 Fertility 定义

不要只报告“平均 token 数”，而要明确归一化单位：

- **tokens / Unicode code point**：衡量对组合字符和稀有字符的切分开销。
- **tokens / Tibetan syllable**：按 tsheg（通常为 U+0F0B，也注意 U+0F0C）分隔的音节近似统计。
- **tokens / sentence**：估算上下文窗口和训练显存。
- **Byte/character compression ratio**：衡量编码压缩程度。
- 平均值、中央値、P95，而不只看平均值；P95 能暴露极长句和异常组合字符。

对每个模型和每种语料分域报告：fertility、未知/异常 token 率、序列长度、超长样本比例、编码速度和显存/内存开销。

#### 2.3.2 藏文特有的预分词问题

藏文的 `་` 更可靠地标记音节边界，但它不等价于中文空格或英文单词边界；一个“词”可能跨越多个音节，也可能存在粘写、标点和异体写法。因此本项目不把“藏文分词”简单定义为词边界识别，而是分三层：

1. **Unicode/组合字符层**：检查 NFC/NFD、元音符号、上下加字和罕见组合符号。
2. **音节层**：以 tsheg 分隔统计音节数和音节内 token 数。
3. **词法层**：若没有可靠人工词边界，不强行构造“金标准词分词”，只做探索性预分段。

实验中要特别检查：

- NFC 与 NFD 是否造成 token 数变化；原始版本和规范化版本都要留档，不要覆盖原始语料。
- tsheg U+0F0B、非断空格变体、tsheg bar U+0F0C 的影响。
- 藏文元音符号和 Mn/Mc 组合字符是否被预分词器拆散。
- 叠加字、罕见佛教术语、人名、数字、单位、标点的长尾行为。
- 论文中指出的“某些基于 `\p{L}+` 的 ByteLevel 预分词会忽略藏文组合标记”的现象；不要把文献中的数字直接当成我们的结论，要在本项目的 NLLB、HY-MT2 和 CS336 上重新测量。

建议做四组对照：NLLB 原始编码、NLLB 仅做 NFC、CS336 Raw BPE、CS336 Syllable-aware BPE。若将藏文插入空格后再喂给 NLLB，只作为消融，不作为默认生产方案，因为这可能改变预训练模型熟悉的分布。

#### 2.3.3 领域/风格分层

将 FLORES、MITRA `bo2zh`、Lotsawa House、MITRA 训练集分别统计，观察：

- 通用现代文本和古典佛教文本的 fertility 是否不同。
- 专名、佛学术语、长复合词是否导致 P95 显著上升。
- 简体目标和繁体/传统目标的中文 tokenizer 统计是否不同。
- NLLB 的 `zho_Hans`/`zho_Hant` 语言标签只是脚本标签，不会自动完成风格转换；风格必须通过数据和评测验证。

## 3. 藏文模块：模型、微调路径与指标

### 3.1 模型角色

| 模型 | 角色 | 当前建议 |
|---|---|---|
| NLLB-200 distilled 600M | 主翻译模型、第一优先级 | 先做推理冒烟，再做 LoRA/小规模微调，最后视显存决定是否全量微调 |
| HY-MT2-1.8B | 本地强基线/参考模型 | 先做少量推理和 prompt 格式验证；有 24GB 以上 GPU 后再考虑 LoRA，不把它作为 CPU 主线 |
| CS336 小型 Transformer | 课程教学与可解释消融 | 用 assignment1 的 BPE 和 assignment4/5 框架训练小模型，重点展示数据和 tokenizer 影响 |

### 3.2 训练顺序

**阶段 A：CPU 预实验**

- 完成所有数据清单、哈希、文档级切分和数据质量统计。
- 跑 NLLB tokenizer 全量统计。
- 在 50–200 条样本上验证 NLLB 端到端翻译代码、目标语言 token、解码和评测脚本。
- 对 HY-MT2 做最小推理检查；只下载并加载必要文件，不在 CPU 上跑大规模生成。
- 在 1k–10k 条小样本上训练 CS336 tiny Transformer（若时间允许）。

**阶段 B：第一张 24GB 级 GPU**

1. NLLB 600M：先 10k pilot，再 100k 标准实验。
2. NLLB 600M：视稳定性和训练时间跑 427,916 条全量过滤训练集。
3. 比较全参数微调、LoRA 或参数高效配置；内存不足时优先 LoRA/梯度累积/梯度检查点。
4. HY-MT2 只做 LoRA 小实验，与 NLLB 分开报告，不混合训练脚本和评价结论。

**阶段 C：可选多卡**

- 使用 2–4 张 4090/5090 加速 NLLB 全量或 HY-MT2 LoRA。
- 多卡不是必要条件；如果只有一张卡，课程项目仍可完成。
- 多卡实验需固定数据顺序、seed、有效 batch size 和学习率，避免把“卡数变化”误认为模型改进。

### 3.3 NLLB 微调实现要求

- 使用 Hugging Face `AutoTokenizer` 和 `AutoModelForSeq2SeqLM`。
- 藏文源语言固定为 `bod_Tibt`；根据目标测试集选择 `zho_Hans` 或 `zho_Hant`。
- 目标端必须显式使用 `text_target` 编码；生成时设置目标语言起始 token。
- 初始 `max_source_length`/`max_target_length` 可设为 256，统计后再决定是否提高到 512；超过上限的样本要记录截断率。
- 采用文档级切分，禁止同一文档的相邻句子泄漏到训练和测试两侧。
- 训练集先采用 MITRA 过滤训练集；FLORES、MITRA 官方两个测试集和最终案例集绝不用于训练或调参。
- 保留原始藏文、原始目标中文和清洗后版本，不能只保存 token ID。
- 记录配置、数据哈希、模型版本、seed、有效 batch size、学习率、训练步数、保存点和评测脚本版本。

建议起始配置（不是最终承诺值）：per-device batch size 1–8、梯度累积、学习率在小范围网格中试验、混合精度和梯度检查点按显存开启；先保证 10k pilot 能稳定收敛，再扩大数据量。全量参数微调只有在显存和训练时间足够时尝试，LoRA 是更稳妥的课程项目主线。

### 3.4 HY-MT2 实现要求

- 使用其官方 tokenizer、`AutoModelForCausalLM` 和官方提示格式。
- 提示中使用模型要求的语言全称，不把 `bod_Tibt` 等 NLLB 语言码直接塞给 HY-MT2。
- 先记录零样本输出、生成速度、显存和格式错误；再决定是否做 LoRA。
- 评测时去除 prompt 和特殊标记，只比较最终中文输出。
- HY-MT2 的结果作为“不同架构/不同预训练语料的参考”，不能与 NLLB 的训练步数或 token 数简单横向等同。

### 3.5 CS336 Transformer 实现要求

建议从 4–6 层、`d_model` 256–512、8k/16k 词表、较短上下文开始；使用 10k 或 50k MITRA 子集验证 pipeline，再决定是否扩大。需要报告：

- BPE 词表大小和训练语料规模。
- Raw Unicode 与 Syllable-aware BPE 的差异。
- 训练 loss、验证 loss、困惑度（如实现了可靠的 token-level 统计）。
- 同一测试集上的 chrF++/BLEU，以及错误案例。

该模型是教学基线，不把低于 NLLB 的分数视为失败；它的价值是能解释 tokenizer、词表和模型容量之间的关系。

### 3.6 评测指标

**自动指标**

- **chrF++：主指标**。以字符 n-gram 为核心，对低资源翻译、藏文形态和中文输出通常比单独 BLEU 更稳健。
- **SacreBLEU BLEU：辅助指标**。必须保存完整 signature，保证不同实验可复现。
- **COMET 或其他本地质量模型：可选**。只有确认模型支持相关语言、许可和本地运行后才使用，不能依赖在线 API。
- 额外记录：输出为空率、重复率、长度比、数字/单位保留率、专名保留率、中文 `<unk>`/异常字符率。

**分域报告**

至少分别报告：FLORES、MITRA `bo2zh`、Lotsawa House、内部验证集。不要只给一个总平均数，因为总平均会掩盖古典佛教文本和现代文本之间的差异。

**人工评测**

对每个主要模型抽取约 100 条，按 1–5 分评价：忠实度、漏译/加译、中文流畅度、术语正确性、风格匹配。由于项目成员可能不懂藏语，人工评测应邀请藏语/汉藏翻译背景的同学或教师；无法立即找到专家时，先把这部分列为“待补充”，不要伪造人工分数。

## 4. 东巴文扩展：图像—中文模型

### 4.1 先明确任务边界

DongbaMIE 并不是传统意义上“东巴文字逐字转写—中文机器翻译”的平行语料。它主要给出东巴手稿图像及中文语义标注，包含四类信息：**对象、动作、关系、属性**。因此课程项目更准确的任务名称应是：

> 东巴文图像的结构化语义理解与中文释读（image-to-Chinese semantic interpretation）

如果后续取得字符级转写、字符框或检测标注，再增加“字符识别/OCR—中文翻译”；在没有这些标注时，不应把 DongbaMIE 的语义生成结果宣传为严格的字符级机器翻译。

### 4.2 数据集与规模

**DongbaMIE（主数据集）**

- 句子级：23,530 对图像—文本样本。
- 官方切分：训练 18,824、验证 2,353、测试 2,353。
- 段落级：2,539 对；训练 2,031、验证 254、测试 254。
- 标注维度：object、action、relation、attribute。
- 官方数据包约 1.92GB，已于 2026-09-24 下载到 `data/raw/dongbamie/`；数据只保存在本地，不上传公共仓库。
- 许可证为 CC-BY-NC-SA-4.0，研究/课程使用需保留署名和相同方式共享要求，不能商业化或重新分发原始数据。

**可选辅助数据**

- Dongba1800：已下载 1,800 张手稿图像及对应标注（train 1,440、test 360），适合检测/定位方向；许可证文字存在冲突，不作为核心训练集的前置依赖。
- DB1404 等单字符/手写数据：只有在确认可访问、许可和标签格式后，才用于字符分类或 OCR 小实验。

### 4.3 建议模型和方法

**主方案：本地 Qwen2.5-VL-3B-Instruct + LoRA/QLoRA**

它适合在课程项目规模上做图像—文本指令微调，3B 版本比 7B 更容易放入单张 24GB 显卡。需要注意 3B 版本的研究许可；若更重视 Apache-2.0 许可而有更多显存，可把 Qwen2.5-VL-7B-Instruct 作为替代，但训练成本明显更高。DongbaMIE 原论文使用 Qwen2-VL 做监督微调，可作为复现参考，而不需要调用论文中的 GPT-4o/Gemini 等在线 API。

推荐采用“结构化优先”的两阶段输出：

1. 输入图像和指令，要求模型输出固定 JSON：`objects`、`actions`、`relations`、`attributes`。
2. 用本地后处理器校验 JSON 字段、去除重复项和格式错误。
3. 再把结构化结果渲染成自然中文“释读”或“翻译式说明”。这一步可以由同一个 VLM 生成，也可以由本地文本模型完成；第一版优先使用规则模板，减少幻觉。

示例指令应类似：

```text
请观察这张东巴手稿图像。只依据图像和标注定义，输出 JSON：
objects、actions、relations、attributes。每个字段使用简短中文短语，
无法确认时填空数组，不要臆造人物、地点或事件。
```

这样做比一开始直接生成长篇中文段落更容易评测，也更符合 DongbaMIE 的标注结构。

### 4.4 东巴文实验顺序

1. 先读取 DongbaMIE 的 README、一个 JSON 标注文件和一张图，确认图像路径、字段、中文文本和四类标注如何对应。
2. 只做句子级 18,824/2,353/2,353 训练；段落级作为扩展，不要一开始把两个任务混在一起。
3. 对图像做统一尺寸、长宽比和缓存策略，避免把图像全部解压到内存。
4. 跑本地 VLM 的零样本或少量样本基线，确认 prompt 和 JSON 格式。
5. 使用 LoRA/QLoRA 做 1–3 个 epoch 的小规模微调；先在 1k–3k 样本上调通，再扩大到官方训练集。
6. 最后再考虑图像裁剪、字符/区域检测、段落级上下文和中文自然化。

### 4.5 东巴文评测指标

- 每个语义字段分别计算 precision、recall、F1：object/action/relation/attribute。
- 分句子级和段落级报告，不能只报一个总 F1。
- JSON 有效率、字段级 exact match、归一化后的 partial match。
- 如果引入区域检测，再报告 mAP/IoU；如果引入字符 OCR，再报告 CER/WER。
- 中文自然化只作为辅助：可报告 chrF/BLEU，但必须同时做人审的语义正确性和幻觉率检查，因为参考中文不一定唯一。
- 切分优先按手稿/来源文档隔离，避免同一手稿的相邻裁剪图像同时出现在训练和测试中。

### 4.6 算力预估

- 当前 CPU：只做数据读取、标注统计、图像可视化和极少量推理，不做 VLM 微调。
- 1×24GB GPU：Qwen2.5-VL-3B 的 LoRA/QLoRA 是合理目标，需小 batch、梯度累积和混合精度。
- 1×24GB GPU：7B 版本更依赖量化和较小图像/序列长度；2–4 张 4090/5090 后再考虑 7B 或更完整的段落级训练。
- 东巴模块不是必须在课程项目第一版完成；若资源不足，完成结构化任务的小子集和严谨评测也足以构成有价值的扩展。

## 5. OCR 与最终平台

平台应采用路由式设计，而不是让一个模型包办所有任务：

1. **输入类型识别**：文本输入先根据 Unicode/脚本统计识别中文、藏文和未知脚本；图像输入先判断是否藏文/东巴文手稿。
2. **藏文图片**：本地 OCR 得到藏文文本，再送入 NLLB；OCR 和翻译分别评测，避免把错误归因混在一起。
3. **藏文文本**：送入 NLLB 主模型；可提供 HY-MT2 作为可选参考。
4. **东巴文图片**：送入 DongbaMIE 微调的 VLM，输出结构化中文释读；若加入 OCR/检测，再显示中间结果和置信度。
5. **统一输出**：中文结果、语言/文字类型、模型版本、置信度和可选的中间 OCR/结构化结果。

第一版平台不追求通用的“任意图片翻译”，而是明确支持：干净藏文文本、藏文文档图像、DongbaMIE 风格的东巴手稿图像。这样更容易把实验结果和 Demo 行为对应起来。

## 7. 需要在实施中持续确认的风险

1. **语料质量**：MITRA 的结构对齐不等于人工语义金标准；所有结论要标注这一限制。
2. **现代风格覆盖不足**：若找不到有许可的现代藏中平行语料，不能声称覆盖全部现代风格，应改为“分域评测 + 风格案例研究”。
3. **中文长尾字**：当前 NLLB tokenizer 审计发现 MITRA 中文目标中存在少量稀有佛教字符，约 2.45% 的目标编码样本出现未知 token；先记录并分析，不要未经实验就修改 NLLB 词表。
4. **模型许可**：NLLB 为 CC-BY-NC；HY-MT2 为 Apache-2.0；DongbaMIE 为 CC-BY-NC-SA-4.0；Qwen2.5-VL-3B 需遵守其研究许可，7B 许可不同，发布 Demo 前必须再次核对。
5. **东巴任务定义**：DongbaMIE 主要是语义抽取，不是字符级翻译；报告中要使用“图像—中文语义释读/翻译”这一更准确的表述。
6. **专家评测**：若没有藏语或东巴文专家，人评只能作为待补项；不能用不懂源语言的评测者给出忠实度分数。
