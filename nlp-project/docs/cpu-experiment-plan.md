# CPU 实验计划

## 总目标

在使用 GPU 之前，完成数据来源核验、文本质量分析、数据划分、分词分析、风格标签设计和小规模 CPU 基线，使后续 GPU 时间主要用于有效训练。

## 资源约束

当前机器有 12 核 CPU、15 GB 内存，但仅约 2 GB 空闲内存。因此：

- 默认逐行或分块读取；
- 初次实验最多抽取 10,000 条；
- 未测量内存占用前，不加载完整 MITRA 或 CUTE；
- 同一时间只运行一个数据处理任务；
- 每一步先输出短摘要，不在笔记本中打印大量原文。

## 阶段 0：项目与数据登记

任务：

- 固定目录和文件命名；
- 为候选数据集登记来源、许可、领域、用途和状态；
- 明确原始数据只读原则。

验收：

- `data/manifests/datasets.csv` 可以被标准库正确读取；
- 每个候选数据集有唯一 `dataset_id`；
- 未确认的许可明确标为 `TO_VERIFY`；
- 未下载的数据明确标为 `planned`、`deferred` 或 `application_pending`。

## 阶段 1：小样本获取与人工检查

首批只处理：

1. FLORES-200 `bod_Tibt` dev/devtest；
2. MITRA Parallel v2 藏中方向的小样本或单个分片；
3. OpenPecha 藏中平行语料；
4. Modern Tibetan Corpus；
5. PublicCorpus 公开的 100 条样例。

每个来源人工查看至少 20 条，记录：

- 字段含义和语言方向；
- 文档、段落或句子 ID 是否存在；
- 领域与文体；
- 是否为真实翻译、自动生成或未知；
- 明显错位、乱码、网页残留和重复。

验收：能够解释每个文件的用途，并决定它只能用于训练、验证、测试还是质量观察。

## 阶段 2：Unicode 与文本质量

藏文检查：UTF-8、NFC、藏文字符比例、`U+0F0B`/`U+0F0C`、组合符、异常空格、混入文字和乱码。

中文检查：简繁体、古今文体、全半角标点、HTML、页码脚注、藏文残留和重复。

验收：每条清洗规则都有修改数量、修改前后样例，并且可以从原始文件重新生成。

## 阶段 3：平行质量、去重与划分

检查空句、长度比、重复句对、一对多异常、方向反转和疑似不平行内容。训练/验证/测试优先按文档或作品划分，并检查训练集与测试集的精确重复和近似重复。

验收：形成过滤统计和人工抽查结果；能够说明测试集不存在明显文档级泄漏。

## 阶段 4：Tokenizer 对比

在相同样本上比较 NLLB、Hy-MT2 和 CS336 BPE：

- 每音节 token 数；
- 每 Unicode 码点 token 数；
- 句子长度分布；
- 组合符附近的碎片化；
- 极端长序列；
- 不同领域之间的差异。

验收：得到可量化结论，不用少量示例替代总体统计；不修改预训练模型原 tokenizer。

## 阶段 5：风格识别 CPU 基线

暂定弱标签为古典佛教、现代正式、现代文学、现代口语/其他。按文档和来源划分，使用轻量字符特征分类器，报告 Macro-F1、每类表现、混淆矩阵和典型错误。

验收：确认模型不是依靠固定页眉、网址或来源格式作弊。

## 阶段 6：CPU 翻译与 OCR 基线

- NLLB-600M：只对 50～200 条样本进行本地 CPU 推理，验证完整翻译和评测流程；
- Hy-MT2-1.8B：CPU 上只做极少量冒烟测试；
- Tesseract Tibetan：对 20～50 张代表性图片建立 OCR 基线；
- CS336 小模型：只验证极小数据的训练管线，正式实验等待 GPU。

验收：文本翻译、OCR 和评测均能端到端运行，且失败样例已保存。

## 阶段 7：冻结评测协议

- 翻译主指标：chrF++；
- 辅助指标：BLEU，并保存 SacreBLEU 完整签名；
- OCR 指标：CER；
- 按古典、正式、文学、口语分别报告；
- 干净文本与 OCR 文本分别报告；
- 人工评价包含忠实度、流畅度、术语、风格和增译/漏译。

验收：在 GPU 训练开始前冻结测试集和指标配置。
